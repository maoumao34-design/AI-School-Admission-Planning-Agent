## 1. 问题与用户

> 对应 DELIVERY §一-1「问题与用户」/ TASK-SPEC §2、§7「场景与范围」。

- **目标用户**：参加高考、需要填报志愿的**考生及家长**（核心）；延伸到**升学规划人员**（一个账号管理多个考生档案，后续增强）。
- **真实场景**：江苏 2026 物理类考生，分数 / 位次 / 选科 / 预算已知，需要在众多院校专业组中筛出**符合硬性资格**、**概率档合理**、**可并排比较**的候选，并在分数/预算/目标变化时快速看到方案变化。
- **三个核心痛点**（TASK-SPEC §2）：
  1. **信息分散且会变化**——院校/专业/计划数/费用/截止时间散落不同官方页面，往年信息不能直接替代本周期。
  2. **资格条件容易遗漏**——选科/学历/先修课/材料/费用等硬条件必须先判，不能凭感觉推荐。
  3. **方案需要持续调整**——分数/预算/地区/目标变化时，候选/差距/风险/时间线要一起变。
- **为何聚焦此范围**：高考志愿是信息高度分散、资格判定强、容错低的典型决策场景；限定**一个省（江苏）+ 一个年度（2026）+ 物理类**可在数据可得性内把"真实来源 + 真规则 + 真重算"做透，而非摊大饼。**不做博士/留学**（范围红线）。
- **成功标准**：代表性案例（江苏 2026 物化 637/5,200）能完整跑通 6 步；改关键条件后候选/方案/依据随之更新；每个结论可展开看依据、规则、官方来源。

## 2. 方案与交互

> 对应 DELIVERY §一-2「方案与交互」/ TASK-SPEC §3、§4、§5。

### 2.1 核心任务流程（端到端 6 步）

| 步骤 | 内容 | 页面 / API |
|---|---|---|
| **01 建立条件** | 填写/追问影响资格的缺失条件与冲突 | `ConditionForm`（结构化表单：省/年度/科类首选+再选/分/位次/学费预算） |
| **02 获取官方信息** | 展示本省本年度真实数据 + 原始来源 | 候选卡 `source.url` + `updated` + `status` |
| **03 资格过滤** | 逐条规则判定，排除不满足硬条件者 | `POST /api/eligibility`（阻断/advisory/needs_review 可展开） |
| **04 方案比较** | 候选/差距/成本/风险 + 多策略并排 | `POST /api/compare`（院校优先/专业优先/均衡排序） |
| **05 改条件重算** | 改一项分数/预算/地区/目标，重跑过滤+规划，对比前后版本 | `POST /api/recompute`（`diff.added/removed/changed`）；前端 debounce 300ms 并行重调 |
| **06 确认导出** | 确认最终方案，导出带来源的行动计划 | `exportReport()` → Markdown（条件/资格/方案/每条来源+时间/三红线声明）→ `.md` 下载 |

### 2.2 对话区 / 工作区配合

- **左侧建条件区**（`ConditionForm`）：结构化收集影响资格的条件；任一字段变化触发随动重算。
- **右侧工作区**（`Workspace` + `CandidateCard`）：结构化候选卡（院校/专业组、批次/层次标签、参考概率档、近 3 年计划数/最低分/位次差、选科要求、学费、推荐理由可展开、官方来源入口、异常提示）。
- **每个响应都带 `trace`**：`conditions_used` / `rules_applied` / `dataset_year` / `generated_at`（决策透明化）。

### 2.3 关键状态 / 异常状态

- `info_insufficient`：缺关键条件 → 给原因 + 下一步。
- `no_result`：无候选通过硬条件 → 给原因 + 下一步。
- `needs_review`：数据待抽取（`tuition`/`plan=null`）或未知规则类型 → **不阻断**，附 `caveat` 标记（避免样本缺值误杀）。

### 2.4 高价值交互设计

**「改条件 → 候选/档位随动 + 前后版本差异」**：改分数/位次/预算后，并行重调 `/api/compare` + `/api/eligibility`，候选、概率档、位次差、资格全部随动；`/api/recompute` 产出 `added/removed/changed` 版本差异。让"方案需要持续调整"这一痛点在页面实时可见。

## 3. 实现与技术

> 对应 DELIVERY §一-3「实现与技术」。只写真正用到的。

| 层 | 技术 | 用途 |
|---|---|---|

| **语言** | TypeScript | 端到端类型安全 |

| **决策引擎** | TS **纯函数**（`src/decision/*`） | 资格校验 / 概率档 / 方案排序（**先过资格再排序**，per-card 选科）/ 改条件重算 / 版本差异；输入相同输出相同，`vitest` 49 用例全绿 |

- **数据集**：`data/sample-jiangsu-2026-phys.json`（扩样至 **8 张候选卡** / 3 所院校：东南 1102、南理工 1104、河海 1105；覆盖冲刺/稳妥/保底 + 跨档 + 跨选科，含 SEU-07「物理+不限」，位次带 ~1600–27000，支撑改分/改选科→候选集变化）。

### 4.2 资格规则（确定性纯函数，不交给 LLM）

每条规则 = 文本规则 → 可机读判据 `machine{type, params}`，引擎 canonical 4 类（见 README 资格规则表）：

| rule_id | 类别 | machine.type | 判据 |
|---|---|---|---|
| `SUBJ-REQ-2024-001` | 选科 | `subject_match` | required:[物理,化学] |
| `BATCH-QUAL-2026-001` | 批次 | `batch` | allowed:[普通类本科批] |
| `FEE-CAP-2026-001` | 费用 | `tuition_le` | max:60000 |
| `PLAN-AVAIL-2026-001` | 计划 | `plan_gt` | min:0 |

**判定原则**：只有「能确定不满足硬条件」才阻断；待抽取/未知类型一律不阻断、改附 `caveat` + `needs_review`。

## 8. 范围决策说明（有据取舍，非漏交）

> 诚实标注本次主动做出的范围取舍，便于评审判断为"有据决策"而非"漏交"。

1. **仅做高考志愿，不含两项共同必做工作流**（游戏营销 / AI 漫剧）：maozh2 确认"只需要完成这个升学 agent"，两项共同工作流后续独立处理（TASK-SPEC §7 已注明）。
2. **国内可达性不做**：默认 `*.vercel.app` 域名即算交付物 1「可直接访问」（已部署、全球可访问）；国内 DNS 对 `*.vercel.app` 有污染，但**不扩到自定义域名 / Cloudflare / 备案**（超出 MVP，maozh2 拍板"不需要国内可达性"）。按**非范围**处理，不写成"已知缺陷"。
3. **手机端真机视觉未单独跑**：响应式 Tailwind 已实现、主页面无明显错位；如实标注，不构成缺陷。
4. **LLM 对话 / 登录隔离列为后置**：核心 6 步零环境变量可跑通；增强项明确标注、未作为已实现。
5. **后端「再选不超过 2」拦截 = 做**（maozh2 seq236 拍板，推翻团队 unanimous「保持前端拦截」建议）：PM 范围界定为**输入校验层**——后端校验「考生提交的再选不超过 2 门」（`secondary>2` 拒、允许 1–2 门；前端被绕过时兑底），**不改 per-card 资格判定、不过滤卡、不动候选集**，使拦截诉求与候选随动两个都成立。用 `>2` 而非 `===2`：样本/测试含 `secondary=1` 门用例，恰好 2 会误阻（群管/AI工程师收敛定 >2）。
